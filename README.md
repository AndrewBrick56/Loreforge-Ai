# LoreForge AI

Transform ordinary photos into extraordinary AI characters — then build a
full memecoin brand kit around them. Next.js 16 (App Router) + TypeScript +
Tailwind v4 + Supabase + OpenAI + Solana.

## Status: Stage 5 complete + Memecoin Branding Studio

**Stage 1–5 (done):** design system, landing page, the Character Creation
Studio, real OpenAI image generation (`gpt-image-2`), the Character Identity
Engine, scene consistency, accounts, database with row-level security,
My Characters, Explore.

## This update: audit + Memecoin Branding Studio

Before building new features, the existing image-generation pipeline was
audited end-to-end.

**🔴 Real gap found and fixed:** the user's original uploaded photo was
never stored — only the AI-generated result was. Fixed via an additive
migration (`supabase/migrations/002_source_photos_and_memecoin.sql`):
original photos and generated images are now stored **separately** in
Supabase Storage, each as their own `character_images` row (`kind='source'`
vs `kind='original'`).

**✅ Confirmed already working:** name/personality/catchphrase/backstory
generation and saving, and character-consistent scene regeneration — no
changes needed there.

### Memecoin Branding Studio (new)
On any saved character's page, the owner can generate, all derived from
that same character's reference image so the identity stays consistent:
- **Token name & ticker suggestions** — pure creative text brainstorming
  (OpenAI structured output), clearly labeled as suggestions only; nothing
  is registered or launched.
- **Square token logo** — transparent background, icon-style.
- **X (Twitter) profile picture** (1:1) and **banner** (3:1).
- **Telegram sticker** — generated as real 512×512 **WebP with a transparent
  background**, matching Telegram's actual sticker format.
- **Reaction memes** — the character image is generated by AI, but the
  caption text is added with a client-side `<canvas>` tool (top/bottom bold
  text, classic meme style). This is deliberate: image models are still
  unreliable at rendering small, legible, correctly-spelled text, so
  captions are composited after generation instead.

All assets land in a public gallery on the character's page and count
toward that character's image limit (raised from 30 to 60 in the migration
to leave room for branding on top of story scenes).

### Solana integration (preparation, not trading)
- A character's owner can **associate an existing token** by mint address.
- The address is validated two ways: (1) format — valid base58, decodes to
  a real Ed25519 public key; (2) **real on-chain check** — a direct call to
  a Solana RPC endpoint confirms the address is owned by the SPL Token or
  Token-2022 program and is an initialized mint (parses the raw account
  layout; no extra `@solana/spl-token` dependency needed).
- If on-chain verification succeeds, the character page shows a "Verified
  on-chain" badge. If the RPC is unreachable, saving still succeeds but is
  honestly labeled "not verified" rather than blocking on RPC flakiness —
  these are intentionally different outcomes (see `checkMintOnChain` in
  `src/lib/solana/mint.ts`).
- **Live market data** — price, 24h change, liquidity, market cap — fetched
  from DexScreener's public API (`/tokens/v1/solana/{mint}`, no key
  required; endpoint confirmed against DexScreener's current docs). Never
  stored in the database, always fetched fresh (30s in-process cache to
  avoid hammering the API). Shows "market data unavailable" rather than a
  fabricated number when no pairs exist yet.
- **This is explicitly NOT**: proof of wallet ownership of the token, token
  trading, or automatic token launches. A creator can associate any real
  token's address with their character as a declared link — full
  wallet-signature-verified ownership is the next stage.
- **Critical security boundary, tested directly:** `verified_on_chain` has
  **no client-facing column grant at all** — not even for the character's
  owner. Only the server, using the service-role key, can ever set it, and
  it does so explicitly on every write. This matters because Supabase
  exposes every table to PostgREST directly, so a client calling the table
  API directly (bypassing the Next.js route entirely) is a real attack
  surface, not a hypothetical one.

### How this was verified
The migration was tested the same rigorous way as the original schema: Postgres
loaded locally, schema.sql + migration applied together, then **26 new
adversarial tests** on top of the original 59 (85 total, all passing),
including:
- A second source photo on the same character is rejected (unique index)
- Mismatched storage path / file extension is rejected
- An unsupported aspect ratio, or a NULL ratio on a non-source image, is
  rejected (caught a real Postgres gotcha here: `CHECK` constraints treat a
  NULL expression result as *passing*, not failing — the constraint needed
  an explicit `IS NOT NULL` guard)
- The 60-image-per-character limit is enforced exactly at the boundary
- A malformed mint address is rejected by the database `CHECK` constraint
- Bob cannot edit or delete Alice's token association (RLS)
- **The owner themselves cannot self-mark their own token "verified"** —
  confirmed this fails with `permission denied` even for the row's owner
- Token visibility follows the parent character's public/private status
- Changing a mint address does not silently inherit a stale "verified" flag

Two real bugs were caught and fixed during this testing (not just written
and assumed correct): a missing column-level grant that broke character
creation entirely, and the NULL-constraint gotcha above. A third bug was
caught via live smoke-testing (not SQL testing): the token market-data route
crashed with an unhandled 500 when Supabase wasn't configured, instead of
degrading gracefully like every other route — fixed to match the rest of
the app's pattern.

### Known limitations, stated honestly
- The on-chain mint check couldn't be exercised against a live Solana RPC
  from this sandbox (network restricted) — format validation and the
  graceful-failure path were verified directly instead. Test with a real
  mint address once deployed.
- DexScreener's endpoint shape was confirmed against their current public
  docs, not tested with a real live token from this sandbox for the same
  reason.
- Token association has no wallet-signature proof of ownership yet — that's
  the next stage.

## Deployment (Vercel + Supabase)

### 1. Supabase (do this first)
1. Create a project. In the SQL editor run, **in order**: `supabase/schema.sql`, then `supabase/migrations/002_source_photos_and_memecoin.sql`, then `supabase/migrations/003_atomic_rate_limits_and_source_images.sql`.
2. **Authentication → URL Configuration:** set *Site URL* to your deployed domain and add `https://YOUR-DOMAIN/auth/callback` under *Redirect URLs*. If you skip this, confirmation and magic-link emails will send people to the wrong address.
3. **Authentication → Providers → Email:** decide whether "Confirm email" stays on (recommended for production).
4. Copy the project URL, anon key and service-role key (Project Settings → API).

### 2. Vercel
1. Push the repo to GitHub and import it in Vercel (framework is auto-detected).
2. Add every variable from `.env.example` in *Project Settings → Environment Variables* **before the first deploy**. `NEXT_PUBLIC_*` values are baked in at build time, so changing one later requires a redeploy.
   Required: `OPENAI_API_KEY`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `GENERATION_SIGNING_SECRET`, `CRON_SECRET`.
3. `vercel.json` registers a daily cron that deletes unsaved drafts older than 24h. It only works if `CRON_SECRET` is set; without it the endpoint refuses all calls.
4. Hosting plan: Vercel's free Hobby plan is restricted to non-commercial use (check their current terms); a client project will normally need Pro.

### 3. Why uploads are capped at 3MB (important)
Serverless hosts cap request and response bodies (Vercel: 4.5MB). Base64 inflates files by about a third, so a 10MB photo could never have reached the server on Vercel. The studio therefore:
- accepts uploads up to **3MB** (enforced in the browser and again on the server), and
- never returns generated images inline when Storage is configured. Results are written to Storage and returned as short-lived signed URLs; "Save" then *moves* the stored object rather than re-uploading it.

Without Supabase configured the app falls back to inline responses (fine for local development; not safe for very large outputs on a capped host).

### 4. Post-deploy click-test (10 minutes, do this before handing over)
1. Sign up, confirm the email, and check the link lands on your domain, not localhost.
2. `/create`: upload a photo under 3MB, describe a transformation, generate. **This is the first real end-to-end OpenAI test; it has never been run with a live key.**
3. Download the result, then Save to collection, then open My Characters.
4. Generate a scene from the saved character; confirm it appears on the character page.
5. Brand Studio: generate a logo, a sticker and a meme; add a caption to the meme and download it.
6. Publish the character, open it in a private window, and confirm it shows on Explore.
7. Associate a real mainnet token mint and confirm the verified badge and market data appear.

### 5. Known limitations
- Live OpenAI generation with a valid key was not testable in the build environment (no key; later the sandbox could not resolve `api.openai.com`). Everything up to the API call is tested, including error handling.
- The on-chain mint check and DexScreener lookup could not reach the network from the build environment; format validation and failure handling were tested.
- The meme caption export draws a cross-origin Storage image onto a canvas, which needs Supabase to return CORS headers for signed URLs. If the export button reports an error, right-click the preview and save the image instead; tell me and I will route the image through the server.
- Token association is a creator-declared link, not proof of ownership (wallet-signature verification is the next stage).
- Production generation limits use the atomic `reserve_rate_limit` database RPC and require valid Supabase URL, anon key, and service-role key settings. If the shared limiter is unavailable in production, generation endpoints fail closed with HTTP 503 rather than silently reverting to a per-instance limiter. Local development can use the in-memory fallback.

## Setting it up

Run the SQL files in order in your Supabase SQL editor:
1. `supabase/schema.sql` (if not already run)
2. `supabase/migrations/002_source_photos_and_memecoin.sql`
3. `supabase/migrations/003_atomic_rate_limits_and_source_images.sql`

Migration 003 is required for existing projects too: it repairs source-photo extension handling and installs the atomic rate-limit RPC expected by the API routes. It also adds a server-only Storage cleanup queue; failed character-image removals are retried by the scheduled cleanup job after it verifies the object is no longer referenced by a character.

Then `npm install`, `cp .env.example .env.local` and fill in your keys, then
`npm run dev`.

## Notes on scope and honesty

Nothing in this project pretends to work when it doesn't. Every route that
isn't backed by a real implementation says so explicitly, every page that
needs missing configuration shows a clear setup notice, and every claim in
this README about what was "verified" reflects an actual test that was run,
not an assumption.

## Re-running Supabase SQL safely

The baseline schema and migration 002 replace existing trigger and policy definitions before recreating them, so those files can be rerun after a partial execution without failing on errors such as `trigger already exists`. Run them in this order: `supabase/schema.sql`, `supabase/migrations/002_source_photos_and_memecoin.sql`, then `supabase/migrations/003_atomic_rate_limits_and_source_images.sql`. Do not skip migration 003 on a deployment using the updated API. Existing tables and rows are preserved.
